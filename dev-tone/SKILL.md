# dev-tone — 사내 개발자 문체로 다듬기

## 문체 규칙

PR 설명, 기술 문서, Jira 코멘트, 리뷰 코멘트 등 사내 엔지니어링 문서를 작성할 때는 AI 어시스턴트처럼 쓰지 말고, 실제 개발자가 작성한 것처럼 자연스럽고 담백하게 작성한다.

기본 원칙:

* 짧고 직접적으로 쓴다.
* 기존 문서, PR, 코멘트의 말투와 용어를 최대한 따른다.
* 같은 팀 개발자라면 이미 알고 있을 내용은 설명하지 않는다.
* 추상적인 효과보다 실제 변경 내용과 동작을 구체적으로 쓴다.
* 불필요한 제목, 소제목, bullet을 만들지 않는다.
* 작은 변경을 과하게 구조화하거나 길게 설명하지 않는다.
* 기존 문장을 수정할 때는 전체를 새로 쓰지 말고, 원래 표현과 말투를 최대한 유지한다.
* 사용자가 별도로 요청하지 않으면 원문의 정보량과 길이를 크게 늘리지 않는다.

다음과 같은 AI 특유의 표현과 패턴은 피한다.

* "이번 변경을 통해 ~할 수 있습니다."
* "이를 통해 ~을 개선할 수 있습니다."
* "이 변경은 ~을 보장합니다."
* "전반적인 안정성을 향상시킵니다."
* "보다 효율적으로 ~할 수 있습니다."
* "추가적으로", "더불어", "나아가", "결과적으로"를 습관적으로 사용하는 것
* "효율적인", "안정적인", "유연한", "강력한", "원활한" 같은 추상적 수식어
* 같은 내용을 서론, bullet, 결론에서 반복하는 것
* 변경 내용을 실제보다 거창하게 표현하는 것
* 문서 끝에 의미 없는 요약이나 마무리 문장을 붙이는 것

PR 설명은 해당 코드베이스를 이미 알고 있는 같은 팀 개발자에게 설명한다고 생각하고 작성한다.

필요한 경우 아래 내용만 포함한다.

* 왜 수정했는지
* 실제로 무엇을 수정했는지
* 리뷰어가 알아야 하는 동작 변경, 호환성, 마이그레이션, 검증 내용

이 구조를 억지로 모두 채우지 않는다. 작은 PR이라면 2~5문장으로 끝내도 된다.

예시:

나쁜 예:
"이번 PR에서는 모델 output 검증 로직을 새롭게 도입했습니다. 이를 통해 잘못된 output 설정을 조기에 감지할 수 있으며, evaluation pipeline의 전반적인 안정성을 향상시킬 수 있습니다."

좋은 예:
"evaluation 시작 전에 model output을 검증하도록 수정했습니다. 기존에는 잘못된 output 설정이 SNR 계산 단계에서야 확인됐습니다."

최종 결과를 작성한 뒤 아래 문장은 삭제한다.

1. 앞에서 이미 말한 내용을 반복하는 문장
2. 개발자라면 당연히 알 수 있는 내용을 설명하는 문장
3. 릴리즈 노트나 홍보 문구처럼 들리는 문장
4. 없어도 의미 전달에 문제가 없는 문장

기본 방향은 "잘 쓰기"보다 "덜 쓰기"다.
짧고 건조한 사내 개발자 문체를 기본값으로 사용한다.

## 입력 소스

인자로 아무것도 주어지지 않으면 **직전 대화에서 사용자가 작성한 텍스트**(PR 설명 초안,
코멘트 초안 등)를 다듬는다.

인자가 주어지면 아래 기준으로 소스를 판별한다:

| 인자 형태 | 판별 기준 | 조회 방법 |
|---|---|---|
| 로컬 파일 경로 | `.md` 등 확장자를 가지거나 `/`, `~`로 시작하는 경로 | Read 도구로 파일 내용을 읽는다 |
| GitHub PR URL | `github.com/<owner>/<repo>/pull/<N>` 패턴 | `gh pr view <N> --repo <owner>/<repo> --json body --jq .body`로 본문 조회. 특정 코멘트를 다듬으려는 것일 수도 있으므로, URL만 주어지고 대상이 불명확하면 추측하지 말고 "PR 본문을 다듬을까요, 아니면 특정 코멘트인가요?"라고 먼저 확인한다 |
| Confluence URL | `atlassian.net/wiki/...` 등 Confluence 도메인 패턴 | 기존 연결된 Atlassian MCP 도구(`mcp__atlassian__getConfluencePage` 등)로 페이지 본문 조회 |
| Claude Artifact URL | `claude.ai/...` 형태 | WebFetch로 내용 조회 |

## 출력 및 반영

1. **항상 먼저** 다듬은 결과를 대화창에 diff 형태(원문 vs 다듬은 버전)로 보여준다.
   이 단계는 소스 종류와 무관하게 공통이다 — 파일이든 PR이든 반영 전에 반드시 미리보기부터.
2. 사용자가 반영을 원하면 원본 종류에 따라 처리한다:
   - **로컬 파일**: 사용자가 반영을 요청하면 git으로 되돌릴 수 있으므로 추가 확인 없이 바로 Edit 도구로 반영한다.
   - **PR 본문**: 반영 직전 "PR #<N> 본문을 이 내용으로 덮어써도 될까요?"처럼 한 번 더
     명시적으로 확인한 뒤 `gh pr edit <N> --body "<다듬은 내용>"`으로 반영한다.
   - **PR 코멘트**: 반영 직전 한 번 더 확인한 뒤 `gh pr comment <N> --body "<다듬은 내용>"`
     (신규 코멘트) 또는 `gh api`로 기존 코멘트 수정.
   - **Confluence 페이지**: 반영 직전 한 번 더 확인한 뒤 해당 Atlassian MCP 도구
     (`mcp__atlassian__updateConfluencePage` 등)로 반영한다.
   - **Claude Artifact**: 이 스킬은 재배포하지 않는다. 다듬은 텍스트만 제공하고,
     Artifact 갱신 자체는 사용자가 별도로 요청하면 그때 Artifact 도구로 처리한다.
3. 사용자가 "텍스트만 달라"고 하면 1번 단계 이후 반영 없이 종료한다.

## 대상 모호성 처리

PR URL만 주어지고 본문인지 특정 코멘트인지 불명확하면 임의로 고르지 않고 먼저 물어본다.
파일 경로가 여러 개로 해석될 수 있는 경우(예: 상대 경로가 여러 위치에 존재)도 마찬가지로
먼저 확인한다.
