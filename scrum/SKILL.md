# Scrum — 데일리 스크럼 문안 생성

## 목적

**스크럼 다이어트.** 매일 "어제 뭐 했더라"를 기억해내는 대신, Jira 상태를 그대로 읽어
공유 문안 4섹션을 만든다.

```
1) 처리한 내용   2) 오늘 할일   3) BLOCKER   4) 협조 필요 / 논의
```

**Jira에 쓰지 않는다. 완전한 읽기 전용이다.** 상태 관리(진행 중 → 검토 중 → 완료)는
사용자가 직접 한다. 스킬은 그 스냅샷을 신뢰하고 문장으로 바꿔줄 뿐이다.

## 상태 매핑 (이 스킬의 전제)

| Jira status | ID | → 섹션 |
|---|---|---|
| `검토 중` | **10094** | 1) 처리한 내용 — 리뷰 올라간 = 내가 친 것 |
| `진행 중` | **3** | 2) 오늘 할일 |
| `Blocked` | **10032** | 3) BLOCKER |
| (티켓 코멘트) | — | 4) 협조 필요 / 논의 |

시간 범위(어제/최근 24h) 개념은 **없다.** 지금 상태가 곧 진실이다.
머지된 티켓을 `완료`로 안 옮기면 다음 날에도 "처리한 내용"에 남는다 — 그건 사용자 규율의 몫이다.

> 참고 상태값(이 스킬이 쓰지 않는 것): `해야 할 일`=10003, `완료`=10004, `Drop`=10105

## 파이프라인 위치

```
/story-to-spec  → 스토리 → Task 여러 개
/add-task       → 구두·문서 요청 → 새 Task
/update-ticket  → 기존 티켓 → 내용 수정·보강
/implement      → 티켓 → 브랜치 → 구현 → PR
/scrum          → 현재 상태 → 데일리 스크럼 문안        ← 이 스킬 (읽기 전용, 파이프라인 밖)
```

## 사용법

```
/scrum              # 기본 — NPP02
/scrum NPP40        # 다른 프로젝트
```

## ⚠️ 반드시 지킬 두 가지 (실측으로 확인된 함정)

### 1. status는 **ID로** 조회한다. 이름 쓰면 조용히 0건 나온다.

```
status = "검토 중"   → 0건   ❌  (사이트에 동명 상태가 있어 엉뚱하게 해석됨)
status = 10094       → 6건   ✅
```

이름으로 조회하면 **에러가 아니라 빈 결과**라서, 아무것도 모른 채 "처리한 내용 없음"
스크럼을 뿜게 된다. 반드시 ID.

### 2. JQL 응답은 **항상 오버플로한다고 가정**한다.

`fields`로 description을 빼도 MCP가 그냥 돌려준다. 티켓 11건에 150KB.
오버플로하면 도구가 결과를 파일로 저장하고 경로를 알려준다 → **그 파일을 `jq`로 파싱한다.**

```
- 인라인으로 왔으면      → 그대로 사용
- 파일 경로가 왔으면     → jq로 필요한 필드만 추출 (아래 Step에 명령 그대로 있음)
- Read로 열지 말 것      → 라인 기반이라 못 자른다
```

## 전체 흐름

```
1. 티켓 조회       JQL 1회 (status ID 3종) → jq로 key/status/parent/summary 추출
2. 코멘트 조회     같은 JQL을 fields:["comment"] 로 1회 더 → jq로 티켓당 최근 3개, 300자 컷
3. 그룹핑          부모 있음 → 부모로 묶고 라벨 재작명 / 부모 없음 → 개별 or 느슨한 묶음 제안
4. 협조 추론       코멘트에서 협조·논의 후보 추출 (없으면 만들어내지 않는다)
5. 초안 출력       터미널에 4섹션 불릿 (표 금지 — 슬랙 복붙용)
6. 보강 질문       "협조 필요에 더 넣을 거 있나요?" → 반영 → 최종 출력
```

## Step 1: 티켓 조회

```
mcp__atlassian__searchJiraIssuesUsingJql
- cloudId: "nota-dev.atlassian.net"
- jql: 'project = {프로젝트키} AND assignee = currentUser() AND status in (10094, 10032, 3) ORDER BY status ASC, key ASC'
- fields: ["summary", "status", "parent"]
- maxResults: 50
```

오버플로해서 파일 경로가 오면:

```bash
jq -r '.issues.nodes[]
       | [.key, .fields.status.name, (.fields.parent.key // "NO-PARENT"),
          (.fields.parent.fields.summary // "-"), .fields.summary]
       | @tsv' "$FILE"
```

`hasNextPage`도 함께 본다 (`jq -r '.issues.pageInfo.hasNextPage'`). true면 다음 페이지를 마저 받는다.

**0건이면 여기서 멈추고 상태 ID를 의심한다.** 진짜로 할당된 티켓이 없는 건지,
JQL이 잘못된 건지 사용자에게 확인한다. 빈 스크럼을 조용히 내지 말 것.

## Step 2: 코멘트 조회

```
mcp__atlassian__searchJiraIssuesUsingJql
- cloudId: "nota-dev.atlassian.net"
- jql: (Step 1과 동일)
- fields: ["comment"]
- responseContentFormat: "markdown"
- maxResults: 50
```

```bash
jq -r '.issues.nodes[] | .key as $k | (.fields.comment.comments // []) as $c
       | if ($c|length)==0 then "\($k)\tCOMMENTS: 0"
         else ($c[-3:][] | "\($k)\t[\(.author.displayName) \(.created[0:10])] \((.body|tostring)[0:300]|gsub("\n";" ⏎ "))")
         end' "$FILE"
```

> `gsub("\n";" ⏎ ")`를 빼면 코멘트 본문의 줄바꿈 때문에 티켓 경계가 무너진다. 넣어둘 것.

- **티켓당 최근 3개, 본문 300자 컷.** 전체를 컨텍스트에 올리지 않는다.
- 300자로 판단이 안 서는 티켓만 `getJiraIssue`로 개별 확장한다 (예외적으로).

## Step 3: 그룹핑

**부모(스토리/에픽)가 있으면 부모로 묶는다. 단 라벨은 부모 제목을 그대로 쓰지 않는다.**

부모 제목은 대개 너무 넓다 — `[EXT] analyze 기능` 아래에 Profiler 연동 5건이 매달려 있는 식이다.
그대로 쓰면 스크럼에서 "analyze 기능 5건"이라는 뭉뚱그린 소리가 된다.

```
라벨 = 자식 티켓들의 공통 주제 (직접 뽑아 쓴다) + (부모키 · N건)
     → "Profiler 연동 (NPP02-5147 · 5건)"
```

**부모가 없으면:**

| 상황 | 처리 |
|---|---|
| 부모 없는 티켓이 1~2건 | 그냥 개별 불릿 |
| 3건 이상 + 제목 키워드가 겹침 | 느슨한 묶음을 **제안**한다 (예: `Phase2 QA 안정화 3건`) |
| 3건 이상인데 주제가 제각각 | 묶지 않는다. 개별 나열 |

- **억지로 묶지 않는다.** 애매하면 개별이 낫다.
- 그룹 라벨은 초안 단계에서 사용자가 고칠 수 있다고 전제한다.
- 같은 부모라도 상태가 다르면 **섹션이 갈린다** (진행 중 → 오늘 할일, 검토 중 → 처리한 내용).
  섹션을 넘어 묶지 말 것.

## Step 4: 협조 필요 / 논의 추론

**코멘트에서만 뽑는다. 없는 걸 만들어내지 않는다.**

코멘트에서 찾을 것:

| 신호 | → 협조 항목 |
|---|---|
| PR URL이 올라와 있음 | "PR #NNNN 리뷰 부탁" |
| "~확인 요청" / "~여쭤보겠습니다" | 그 대상에게 물어볼 것 |
| 결정을 바꿨다는 서술 | "이 결정 리뷰에서 봐주세요" |
| 외부 의존·환경 문제 (엔드포인트 차단, 접근 권한, 버전 미배포) | 인프라·타 팀 협조 요청 |
| 담당 변경 / 일정 압박 | 조율 필요 항목 |

- PR 번호는 **코멘트 본문에서 파싱**한다. `gh` 호출은 하지 않는다 (다이어트).
- 사람을 지목할 때 **대명사를 쓰지 않는다.** "PR #2550 작성자에게" 처럼 역할로 쓰거나,
  코멘트에 이름이 명시돼 있으면 `{이름}님` 으로.
- 코멘트가 없는 티켓에서는 아무것도 추론하지 않는다.
- 추론 항목마다 근거 티켓 키를 앞에 붙인다 — `[7719] ...`

## Step 5: 초안 출력

**표를 쓰지 않는다.** 슬랙에 그대로 붙일 수 있어야 하므로 불릿 텍스트만.

```
🗓 데일리 스크럼 · {YYYY-MM-DD} · {표시이름}

■ 처리한 내용 (리뷰 대기)
 · {그룹 라벨 또는 티켓 요약} — {티켓키} / PR #{번호}
 · {그룹 라벨} N건
   {요약}({키}) · {요약}({키}) · {요약}({키})

■ 오늘 할일
 · {그룹 라벨} ({부모키} · N건)
   {하위구분}  {요약}({키}) · {요약}({키})

■ BLOCKER
 · {티켓키} {막힌 내용 — 코멘트에 사유 있으면 인용} / 없으면 "없음"

■ 협조 필요 / 논의
 · [{키}] {협조 요청 내용} — {PR·문서 참조}
```

작성 규칙:

- 티켓 제목의 `[SWE]`·`[SWE][fix]` 접두는 **떼고** 쓴다 (스크럼에서 노이즈).
- 티켓 키는 뒤에 붙인다. 프로젝트 접두는 그룹 헤더에 한 번만, 개별은 숫자만 (`7716`).
- 한 줄이 길면 두 줄로 접되, 들여쓰기로 종속을 표현한다.
- **BLOCKER가 없으면 "없음"이라고 명시**한다. 섹션을 지우지 않는다 (매일 같은 4섹션 유지).
- 날짜는 오늘, 표시이름은 조회 결과의 `assignee.displayName`을 쓴다.

## Step 6: 보강 질문 → 최종

초안을 출력한 뒤 **평문으로** 묻는다 (`AskUserQuestion` 아님 — 열린 추가 입력이므로):

> 협조 필요 / 논의에 더 넣을 거 있나요? 티켓에 안 적힌 건 제가 못 봅니다.
> (없으면 "없음"이라고만 하시면 이대로 확정합니다)

- 사용자가 항목을 주면 4번 섹션에 추가하고 **전체 문안을 다시 한 번 통으로 출력**한다
  (복붙 대상이므로 조각내지 않는다).
- 그룹 라벨·문구 수정 요청도 여기서 함께 받는다.
- "없음"이면 초안이 곧 최종이다. 다시 출력하지 않는다.

## 핵심 원칙

| 원칙 | 이유 |
|---|---|
| **Jira에 쓰지 않는다** | 상태 관리는 사용자 몫. 스킬이 상태를 옮기면 진실의 출처가 흐려진다 |
| **status는 ID로** | 이름 조회는 에러 없이 0건 → 빈 스크럼을 모르고 뿜게 됨 |
| **응답은 파일 → jq** | description이 딸려와 항상 오버플로. Read로는 못 자름 |
| **코멘트에 없으면 안 만든다** | 4번 섹션의 신뢰도가 이 스킬의 값어치. 지어내면 스크럼에서 깨짐 |
| **표 금지, 불릿만** | 슬랙에 붙일 물건이다. 표는 슬랙에서 깨진다 |
| **억지로 묶지 않는다** | 압축이 목적이지 뭉뚱그리기가 목적이 아니다 |
| **BLOCKER 없어도 섹션 유지** | 매일 같은 4섹션이어야 읽는 사람이 훑기 쉽다 |

## 주의사항

- **읽기 전용.** `editJiraIssue`·`transitionJiraIssue`·`addCommentToJiraIssue`를 호출하지 않는다.
- 조회 결과 0건이면 멈추고 확인. 빈 스크럼을 내지 말 것.
- 코멘트 300자 컷으로 부족한 티켓만 개별 확장. 전체를 통으로 올리면 컨텍스트가 터진다.
- `hasNextPage`가 true면 다음 페이지를 마저 받는다 (티켓이 50건을 넘는 경우).
- 사람 지칭 시 대명사 금지 — 역할(`PR 작성자`) 또는 `{이름}님`.
- 티켓이 여러 프로젝트에 흩어져 있어도 **인자로 받은 프로젝트 하나만** 다룬다.
  다른 프로젝트가 필요하면 `/scrum NPP40` 처럼 따로 돌린다.
- 상태 ID는 이 사이트 전역(global transition)이라 프로젝트가 바뀌어도 동일하다.
  단 다른 사이트에서는 `getTransitionsForJiraIssue`로 다시 확인해야 한다.

## 관련 도구

- `mcp__atlassian__searchJiraIssuesUsingJql`: 티켓·코멘트 조회 (Step 1·2)
- `jq` (Bash): 오버플로 응답 파싱 — 이 스킬의 기본 경로
- `mcp__atlassian__getJiraIssue`: 코멘트 300자로 부족할 때만 개별 확장
- `mcp__atlassian__getTransitionsForJiraIssue`: 상태 ID 재확인 (다른 사이트·워크플로 변경 시)

## 관련 스킬

| 스킬 | 관계 |
|---|---|
| `/story-to-spec` · `/add-task` | 여기서 만든 티켓이 스크럼 문안의 재료가 됨 |
| `/implement` | 진행 중으로 옮겨지는 티켓을 만드는 쪽. 이 스킬은 그 결과를 읽기만 함 |
| `/update-ticket` | 스크럼에서 나온 논의를 티켓에 반영할 때 이어서 사용 |
